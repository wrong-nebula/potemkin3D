**@patch_gg** · village blockout + FLUX 3 Klein + Fibo 2 · 128 views on fal, $4.44, 26 minutes, one view at a time.

**Good for realistic buildings seen from a few metres or more:** third-person and top-down games, trailers, big backdrops, and a first look at a level. **Not for stylised looks:** it's a photo painter, so it adds grime and uneven colour. **Not for the ground at a first-person player's feet:** that blurs, because the whole level shares one texture.

trompe plans cameras where a player can stand, has an image model paint what each one sees, projects every painting
back onto the level and bakes one texture. It paints under overcast light, so the texture comes out as albedo and your
engine lights it with real shadows. A material model can then read the texture and add normal and roughness maps, so
that light also picks out stonework, frames and shutters. Planning, projection and baking run in your browser on your
GPU; the models run on [fal](https://fal.ai).

## Quick start

```bash
npm install
npx playwright install chromium               # for the headless scripts below
echo "FAL_KEY=your-fal-key" > .env.local      # used by the dev server's fal proxy (or: export FAL_KEY=...)
npm run dev                                   # http://localhost:5178
```

To use it:
1. Pick a sample level (Village, Courtyard, Hall, Loft, Luxor, Hangar) or drop in your own `.glb`. It needs UVs and Y up. Name its parts if you can (glTF material names such as "house walls" or "stone steps"): the prompts read them. A level that names nothing is split into its connected shapes and a vision model names those before painting (about $0.10 for the Courtyard); the **Parts** list shows the names and lets you correct them.
2. Describe the look you want, as materials ("weathered limestone and ochre plaster walls, terracotta roofs"). Don't name objects: anything named here, like a fountain or a market stall, gets painted onto walls.
3. Press **Plan cameras**. It's free, and shows the most the run can cost, about how long it takes, and the share of the texture players' cameras can see at all.
4. Press **Texture level**. Each view is written to `runs/<id>/` as it's painted, so a closed tab loses nothing you paid for: pick the run under **Saved runs** to open it again. Every view is also checked against the blockout in the tab (SAM 2.1 tiny; the first run fetches about 80 MB of weights). Faces the model painted over are held back, and the same camera has a second go at them once the planned views are done.
5. Optional: **Make normal + roughness maps** (about $0.17 for 4K maps) and **Bake ambient occlusion** (free, 15 to 30 s). Switch the display to **Lit** and move the sun to see what they add.
6. **Walk the level** to judge it from where a player stands: W A S D, Shift to run, Space to jump, Esc to leave.
7. Download the textured `.glb` (it carries the maps), the texture or the maps.
8. Build your game on it and [publish it on Patch](#publish-it-on-patch).

If you leave the fal key field empty, the dev server adds `FAL_KEY` server-side and the browser never sees it. It reads the key from the environment or from `.env.local`, which git ignores. A key typed into the field is kept in that browser and sent straight to fal.

Headless, from the command line, the run is saved to `runs/<id>/`:

```bash
node scripts/texture.mjs --level samples/village.glb --id village --views 90 --spacing 3.5 --aerial 8 --roofs 24 --holes 12 \
  --atlas 8192 --style "a sunlit Mediterranean hill village: weathered limestone and ochre plaster walls, ..."
```

Add `--plan-only` to get a free quote first: it picks the cameras in about a second, calls no model and prints the number of views. Each view costs 1¢ to 4¢ and takes about 10 seconds. Every view is saved as soon as it's painted, so a run that dies keeps what it paid for: `--resume <id>` picks it up.

The blockout check is on by default, with one second go per view that needs it (one more fill-model call each) and the plane test (one MoGe-2 call, about 1¢, per view with a big flat face). `--check-retries 0` skips the second goes, `--no-planes` the plane test, `--check-threshold 0.4` lets more through, and `--no-check` turns the check off. `--no-names` keeps a level that names none of its parts unnamed.

Add `--pbr` to make normal and roughness maps once the texture is done, or make them later for any saved run:

```bash
node scripts/pbr.mjs --level samples/village.glb --run village --atlas 8192       # --quote prints the price and stops
```

It writes `normal.png` and `orm.png` (glTF's packing: roughness in green, metalness in blue) to the run's folder and exports `level_textured.glb` again with both. Maps are 4K by default (`--size`), which is four calls and about $0.17.

`--ao` (on either script) also bakes ambient occlusion into the red channel of `orm.png` and the material's occlusion texture. It needs no model: `node scripts/pbr.mjs --level samples/village.glb --run village --ao-only` bakes just that, without a fal key.

On Windows the script runs through ANGLE's D3D11 backend (`TROMPE_ANGLE` picks another). `TROMPE_CHROME` points it at another Chromium or Chrome if Playwright's own isn't installed.

`--full` turns on the later passes together, at the settings they were measured with: a clean-up pass (`--cleanup 10`), hard parts textured on their own (`--parts 5`) and the finishing fill (`--finish`); a flag given by hand wins. The floor pass is not in it: add `--floors 12` for plain ground such as concrete. A run whose page dies resumes itself from the views already on disk, up to three times.

To see what a run's cameras delivered, `node scripts/measure.mjs --level samples/courtyard.glb --run <id>` replays it (no model call) and prints, per view, how the frame was spent (sky, context, grazing, the share that became texture) and, over the texture, how sharply it is sampled in view pixels per texel. It prints how much of the texture a player can see from anywhere they can stand and how much of that is painted, which says how finished a level looks (the share of the whole texture painted does not: on the samples half or more of the texture is surface nobody sees). It also prints the detail a player gets on the surface in pixels per metre, the lesser of what the views captured and what the texture holds; `--layout file|seen` and `--atlas` replay the run into another texture layout or size to compare them. Camera planning is judged by these numbers.

A place that is not a town of plastered houses brings its own look file, `--look samples/luxor.look.json`: its level, lighting and texture size, the look in words, how the prompts speak of such a place (`setting`: which surfaces may carry flat detail and what detail, what must not be added, what a gap is filled with, the light) and photos of the real place (`styleImages`). Every view is sent the photos beside its render, as many as its model takes (four for MiniMax H3, three for FLUX 3 Klein; each adds about $0.008 to an H3 call), and is told to take from them what the surfaces are like and nothing else. Close shots of surfaces serve best. Tone them first: `python3 scripts/reference_tones.py references/luxor/raw references/luxor` flattens each photo's light and brings its stone to the colour of the first, so a photo in hard sun, one in blue shade and one under a floodlight become one stone, close to albedo. A flag given by hand wins over the file.

To try prompt or model changes cheaply before a full run, `scripts/prompt-test.mjs` repaints chosen views of a saved run, with the texture rebuilt up to just before each one. It can also paint roof passes on top of the finished run, and it saves every image to `runs/<run>-ab/<tag>/`. `--dry` writes the prompts and inputs without calling any model.

To fill whatever a saved run still misses (or to carry on with one that was cut short), `--resume <id>` plans views only where the texture is missing or poor and paints on top, in place. For example: `node scripts/texture.mjs --level samples/village.glb --resume village --views 30 --aerial 8 --atlas 8192`. `--parallel 6` paints non-overlapping views at the same time, which is faster but leaves visible seams where they meet.

On WSL2, `scripts/browser.mjs` points headless Chromium's ANGLE at Mesa's D3D12 driver, so runs use the real GPU instead of SwiftShader.

## Publish it on Patch

Built a game on a level trompe painted? Publish it on [Patch](https://patch.gg), where people play and remix browser
games and mods. Install `pch`, Patch's command line, then restart your coding agent and ask it to publish the game: the
install gives every agent on your PC Patch's tools. Or run it yourself:

```bash
npm i -g @patchgg/cli      # or: curl -fsSL https://patch.gg/install.sh | sh
pch login
pch init                   # in your game's folder; it says what's next
pch publish
```

Publishing needs [Patch Desktop](https://docs.patch.gg/get-started) open on a Windows PC: it plays the game once to
test it before it goes live.

## How it works

| Step | Where | What |
|---|---|---|
| Unwrap | `src/core/unwrap.ts` | Automatic (`--unwrap auto\|always\|off`). When a `.glb` arrives with missing, overlapping or zero-area UVs, `xatlas` (WASM) cuts normal-aware charts with angle-preserving parameterisation and feeds them straight into `layout.ts` and multi-page packing; levels whose UVs already pass keep them untouched. |
| Weigh & Walk | `src/core/surface-weights.ts`, `src/core/player-paths.ts` | Optional (`--weights`, `--paths`, `--cavity`). Computes per-face cosine openness/AO, signed dihedral convex curvature, static sun/sky visibility and semantic class (`floor`, `wall`, `ceiling`, `roof`, `organic`, `hard-surface`), alongside a capsule-cleared 2.5D navigation graph walked by simulated bots whose 9-ray frustum gaze ranks surfaces continuously in `[0, 1]`. Both weight UV island sizing (`seen` / `near`), camera selection and defect/part repair priority, and can be inspected as false-colour viewer overlays. |
| Lay out | `src/core/layout.ts` | Optional (`--layout seen`, or the layout menu). A level's UVs usually give the underside of a crate as much texture as the wall beside the door. Rays from where players can stand (spots 2 m apart, up to 60 m, not at a graze) mark each triangle seen or unseen. Unseen triangles are cut into UV islands of their own and drawn at 0.3 of their size, then all islands are packed again (a skyline packer, no rotation) at the largest scale that fits. Islands keep their shape and their size relative to each other. The new seams run between a face that is seen and one that isn't. On the samples the seen faces get 1.41× (Courtyard), 1.31× (Hall) and 1.14× (Village, whose UVs were already weighted by hand) the texels along each side; under 1.1× the file's UVs are kept. The exported GLB carries the new UVs. A saved run can be loaded on either layout, since its views are projected again; maps made for it only fit the layout they were made on. With `--pages 4` (or 16) the level is painted over that many textures of `--atlas` px each instead of one: the islands are packed again over a grid of pages, each island wholly on one page and all at one scale, so every page has the same texel density and no page's edge runs through a face. A view paints every page it sees in the same pass, and the planning, fills and maps keep working on the one texture space the pages make up, so nothing differs from page to page. The post hall sample gets 2.6 times the texels per metre from four pages (four times the area, and a tighter pack). No island can be drawn larger than a page, so before packing, an island longer than half a page (at the scale that would fill the pages) is cut into equal pieces along straight lines of the texture; a face the line crosses is cut in two there, which gives the level a few more triangles for the same surface (the post hall's 7,462 become 7,726 for four pages and 8,374 for sixteen). Without that the hall's floor, one island, held sixteen pages to 3 times the density; with it they give 5.3 to 5.75 times, every page two thirds to three quarters full. Both sides of a cut are painted from the same views: measured on the floor, a cut adds about 0.6 levels of 255 to the difference across it. The level is exported as one mesh with a material for each page. `--layout near` goes further than `seen`. It joins flat faces that share a whole edge into strips, the way a box's sides unfold into one band, so the four sides of a window bar are one island with one gap round it and not four (the post hall's 3,288 islands become 1,682; nothing is stretched, and only faces of the same part and scale are joined). Then it draws each island at the size its nearest onlooker needs: full size when a player gets within 3 m, smaller in proportion beyond that, down to 0.3. On the post hall's one 4096 px texture the faces go from 44% of the texture to 77%, and what is near gets 1.5 times the texels per metre; in stills the floor close up came out 1.2 times sharper and the ceiling 5% softer. It combines with `--pages`. |
| Plan | `src/core/planner.ts` | Sample walkable floors at eye height. Drop spots inside solids or out in the open (rooftops). Join spots a player can walk between (following the floor, so stairs count) and keep the play areas. Render cheap probes from 8 headings per spot, then pick cameras greedily until most reachable surface is captured well. Two experimental switches change this: `--look-at 2` adds candidates aimed at each patch of surface from the two nearest spots that see it from the front (75° lens, within 25° of level), and `--objective sharpness` scores each candidate by the detail it would add (the gain in view pixels per texel, capped at 1, over the cells it sees, times how likely a model is to paint that frame faithfully). `--plan-only` prints what a plan would deliver either way, without painting. Each camera is ordered to overlap what's already painted. Roofs get their own close, drone-style cameras (`--roofs`, 15 m out, 50° down, facing each slope), chosen the same way over roof surfaces only. Then `--aerial` cameras pick up what's left, with their own budget: a high ring looks down at the tops of props and the ground behind them, and a low ring outside the level faces the outer walls. Paint order: players' views, then roofs, then the rings. Last, a hole pass (`--holes`) looks for texels nothing has painted (ground hidden behind props from eye height, tops of props, what the planned views missed). Its candidates are level cameras at eye height aimed at each unpainted patch from its front, plus cameras 5 m above where players stand and the high ring. Each is scored by the unpainted pixels it sees times how likely a model is to paint that view faithfully (`src/core/paintability.ts`: steep pitch, one blank face with no context, and mostly-sky frames score low), times how that kind of camera has fared so far in the run. A candidate expected to turn under 3% of a frame into texture isn't paid for. Those views paint only the holes. |
| Floor | `src/core/planner.ts`, `pipeline.ts` | Optional (`--floors 16`, or the ground checkbox). From eye height most of the ground is seen at under 20°, so its texture comes out stretched three times or more along the view. The floor pass paints it first, from cameras hanging 3.5 m over the player spots and looking straight down (lower under a ceiling), chosen like the other passes but over ground surfaces only, each overlapping the ones before. The prompt says it is the ground seen from directly above and how many metres the image shows (`--floor-style` names the material); without that the models turn the render into a street scene. Only ground pixels are projected: from above, walls are slivers. These views skip the blockout check, whose segmenter picks single stones out of a uniform floor. The players' views that follow see the ground already painted and keep it. |
| See | `src/core/clay.ts`, `views.ts` | Lit gray render per camera (sky light, a soft key light, screen-space AO), plus per-pixel position, normal and UV buffers. The "state" image is the clay render with already-painted texture composited in. By default the clay is lit like an overcast day, with no cast shadows, and the prompts ask for soft overcast light. That's why photogrammetry is shot under cloud: the texture comes out close to albedo. `--lighting outdoor` paints under a sun and bakes its shadows in. It looks photographic from that one sun, but each view paints the shadows a little differently, and they can't be relit. |
| Name | `src/core/parts.ts`, `src/core/naming.ts` | Only for a level that names none of its parts (one mesh, one material). It is split into its connected shapes: triangles that share a corner are one shape, so a house built as a box is one and a bollard standing on the ground is another. Each shape is rendered highlighted in the clay level, from the camera that shows it with something around it (a player's spot before a raised one), and a vision model on fal is asked in a few words what it is. The names feed the prompts like part names from a file. On six Courtyard cameras painted from bare clay, that took the share of the work the painter replaced with something else from 12% to 0%, and what it merged into a neighbour from 8% to 6%. A shape holding over 40% of the level's surface is a shell (a whole hall): its up-facing pixels are called floor. |
| Prompt | `src/core/semantics.ts`, `src/providers/models.ts` | Each view's prompt is built from the level's part names (glTF material names, else mesh names, else the names given to its shapes). It lists the parts in the area to paint with rough positions ("house walls (left), stone stairs (bottom)"). Flat details such as windows, doors and stonework are allowed, but nothing may stick out or be added (awnings, stalls, signs, lamps and so on) unless the level models it. The look is materials only. Roof views get a roof-tile prompt, a mask covering only the roofs, and project nothing else. |
| Paint | `src/providers/` | Every view goes to FLUX 3 Klein ($0.009 at 1024 px, $0.014 at 2048 px), which is told what the result looks like and keeps the camera and the geometry; what was already painted is put back over its answer. Fibo 2 Edit, a masked fill ($0.04, about a megapixel), was the fill model until a bake-off on the Loft: on seven views it painted over 26% of the blockout where Klein painted over 1 to 5%, inventing walls and its own glazing bars; on four Courtyard views the two scored the same. `--fill fibo2` brings it back. Repainting the whole Loft with Klein for every view took 46 views and $0.78 where the run with Fibo fills had taken 61 and $1.76, and the glazing bars ghosted across the buildings outside are gone; it left a little more unpainted (7.7% of what players see against 5.5%). Views with under 3% unpainted are skipped. Views run one at a time, so each sees everything painted before it. |
| Check | `src/core/fidelity.ts`, `src/providers/sam.ts` | Image models like to repaint the scene instead of the surfaces: a prop becomes paving, a flat wall becomes an alley with sky. The geometry buffer says which faces a view shows (regions bounded by silhouettes and creases). For each face the view was to paint, SAM 2.1 tiny is clicked once at the face's innermost point on the generated image and offers masks at three scales. If one overlaps the face by half (IoU), the face was painted as a surface of its own. If not, it was painted over, in one of two ways. **Replaced:** no mask even contains the face, because something else was painted there (sky, a street). That never goes onto the level. **Merged:** a mask contains the face but reaches well beyond it, because the model carried the wall or the paving across it. That is held back while the view has a second go coming: the same camera paints again after the planned views, only what is still unpainted, with a prompt that says the shapes are parts of their own. What is still merged then is accepted, since it is at least one coherent surface. The model runs in the page through WebGPU (or on the CPU), about a second per view on an M1, and costs nothing per view. fal's hosted SAM 2 gives one mask per click, which isn't enough: a single click lands on one cobblestone, and several clicks per face miss a wall painted as a street scene. **Plane test:** the masks let one kind of scene through, a single painted object that fills a face (a corner building across a flat wall). So big flat faces (over 10% of the frame) are also tested with MoGe-2 on fal, which predicts camera-space normals from the painted image: where over half of a face is more than 35° off the face's true normal, or has no surface at all (sky), the face counts as replaced. On faithful paintings 0 to 15% of a face is off; on a scene painted across a wall, 94 to 99%. |
| Clean up | `src/core/defects.ts`, `pipeline.ts` | Optional (`--cleanup 10`), after the hole pass. A defect map marks the texture cells a player can see that are unpainted, or poorly captured: holding under 40% of the detail a player's eye at the best spot could get, capped at what the texture can hold (a view pixel per texel), so a wall that is sharp enough is not a defect because someone could walk right up to it. Defects are gathered into patches, cameras are aimed at each from player spots 2 m apart, and each view paints only what it would capture clearly better than the texture has. On the painted Loft, 10 such views ($0.15) took the defects from 10.5% to 8.8% of what players see. The share left is thin parts and corners, where the check still holds much of the painting back. |
| Ground | `src/core/ground.ts`, `atlas.ts` | Optional (`--ground 3`, or `scripts/ground.mjs` on a saved run), after the views; about $0.014 a tile. The ground is laid as a material and not from views. One tile of it is painted from straight above on a plain gray image, with a still of the ground as the eye-level views painted it as a second image to match (without the still the tile came out as squared setts where the views had painted rounded cobbles). Two more tiles are the same stretch of ground, stone for stone, dirtier and more worn. Every texel of ground (what faces up at the height most players stand at, or the up-facing faces of the parts named with `--only`) then takes its colour from its place in the world. Three things keep it from reading as one picture repeated. The ground is divided into patches about a metre across, each with its own piece of the tile, shifted and (for a tile without a grain: `tileGrain` reads that from the tile) turned at random, and blended into its neighbours with weights that keep the tile's contrast. Which state of wear shows where changes in zones a few metres across and towards walls. And the level adds its own: grime gathers where walls and props stand (rays from just above the floor), and the ground keeps the slow changes in brightness the views gave it (not their colour, which a bad view can get wrong). The tiles are brought to the tone of the painted ground, so they sit with the walls. `--span` sets how many metres a tile covers and so the size of the stones; laying the same tiles again with another span, patch size or amount of dirt (`--reuse`) costs nothing. The tiles are kept in the run's folder and the ground is laid again when the run is loaded. |
| Parts | `src/core/partpass.ts` | Optional (`--parts 5`), before the finishing fill, $0.30 a part. The parts with the largest share of what players see still unpainted (and that are one object: not parts that make up much of the level, and not parts built of a few huge faces, such as a house blocked out as one box, which a texturing model paints as a small object) are cut out as meshes of their own and sent to Meshy's retexture with their name, the level's look and, when the views painted enough of the part to show it, a still of the part in the painted room (from a player spot on the part's own floor that sees the most of it painted). It returns the same triangles textured on every face; where a model drops triangles they are matched by position. The texture is brought to the tone the room's views gave the part (its mean colour scaled to theirs). A texture made to match a still replaces the whole part when over 15% of what players see of it was unpainted: on a patterned prop, two textures that do not line up (the views' planks beside the model's) read as displaced. One made from words alone only fills what no view painted. On the Loft, five parts (joists, window frames, beams, crates, duct) took the share of what players see left to the finishing fill from 9.3% to 5.0%. The textured parts are kept in the run's folder and go back on when it is loaded. |
| Finish | `src/core/finish.ts` | Optional (`--finish`), last, and free. Whatever no view painted takes its own part's colours: the nearest painted texel of the same part across that part's surface in the texture, fading to the part's average colour over a short reach (a long run of copied texels reads as a smear, an average does not), and the average of everything for a part with nothing painted. What is left after the painting passes is mostly thin, uniform structure (the inner faces of beams, glazing bars, the sides of joists), whose material is already on the rest of the part. The fill is stored at a token quality, so it shows in the texture and the export but any later view still paints over it and the clean-up pass still aims at it. On the Loft it took what players see from 90.3% painted and the rest bare to 90.3% painted, 9.3% filled and 0.4% bare (slivers thinner than a texel, which the gutter padding covers). |
| Paste | `src/core/composite.ts` | Known pixels are kept exactly. The new image's colours are shifted by how far the model drifted on the known pixels along the seam (a push-pull fill of that difference, fading over ~120 px), then it fades in over 10 px. Any part of the area the model hands back unchanged (still gray clay) is left out of the projection, so the gray never passes for paint and a later view or the hole pass gets another go at it. |
| Project | `src/core/atlas.ts` | A UV-space pass writes colour into each texel this camera sees better than whatever is stored. Quality is `(lens × cos(angle)) / distance`, and pixels within 6 px of a silhouette count at 0.3x, so a better view replaces them. Texels captured at under 0.4x a later view's quality get regenerated. A view can be limited to some of its pixels (transparent, premultiplied); roof passes use this. |
| Consolidate & Refine | `src/core/consolidate.ts`, `src/core/uv-refine.ts`, `src/core/jbu.ts`, `src/core/texfusion.ts`, `src/core/gaussian-field.ts` | Optional (`--consolidate`, `--uv-refine`, `--texfusion`, `--gaussian-field`, `--sds-polish`). `consolidate` back-projects views with silhouette-depth continuity (and optional tangent-plane bilateral soft back-projection), solves an MRF view-label assignment along low-discrepancy contours, registers overlapping detail via Lucas-Kanade tangent flow and stitches seams via a 3-level multigrid Screened-Poisson solver with Joint Bilateral Upsampling (`mrdoob/three.js#35602`, bringing seam ratios to ~1.00 without cross-crease bleed). `uvRefine` links 3D-adjacent UV chart perimeters, inpaints pockets, regresses out baked directional shading and sharpens high-importance sightlines. `gaussianField` fits a degree-1 SH surface Gaussian field to flag outlier views and disentangle glare, while `texfusion` and `sdsPolish` drive local step denoisers. |
| Critique & Loop | `src/core/critic.ts`, `automation/agent.mjs`, `automation/dcc.mjs` | Evaluates player-visible painted share, high-rank sightline `px/m`, multi-view RGB consistency + 3DGS outlier views, seam ratio, SAM/MoGe held-back residuals, diagnostic screenshot artifacts and baked shading (`0–100` score), gating targeted `consolidate` (`dropViews`) / `topUp` / `repair` / `parts` / `uvRefine` rounds under a human-approved dollar budget over CLI and stdio MCP (`agent-plan` → `agent-approve` → `agent-act`) and pushing completed PBR bundles live to Blender/Unreal (`dcc-sync`). |
| Light | `src/core/viewer.ts` | The **Lit** display mode uses the texture as albedo under a real sun with shadow maps, directional bent-normal sky/bounce irradiance and Jimenez cone specular occlusion, so shadows and indirect light match the geometry. The sun sliders move them live, and the normal, roughness and metallic maps shade the surfaces once they've been made (the **Relief** slider scales them). The **Textured** mode shows the texture as painted. |
| Relief & PBR | `src/core/pbr.ts`, `src/core/aligned-maps.ts` | Optional (`--pbr`, `--pbr-mode auto|intrinsic|patina`). Either runs a $0 albedo + 3D geometry intrinsic decomposition (`estimateIntrinsicPbr`, conditioning height, roughness, metallic, micro-normals and convex-edge wear on `openness`, `curvature`, `faceClass` and `materialPresets`, automatic under `--provider local`) or predicts tiles via [PATINA](https://fal.ai/models/fal-ai/patina) fused with intrinsic metallic/edge-wear channels. Packs aligned `orm.png` (occlusion R, roughness G, metalness B) and exports separate linear channels (`exportPbr`). |
| Occlusion | `src/core/ao.ts`, `src/core/fast-sdf-ao.ts` | Optional, and free (`mode: 'fast-sdf'` default). Hybrid [Fast-SDF-AO](https://github.com/wrong-nebula/Fast-SDF-AO) builds a 1-Lipschitz-culled isotropic `R16F` SDF plus a quantized `RGBA32UI` 8-bin SAH local Contact BVH and traces `Halton(2,3)` + IGN hemisphere rays on WebGL2 GPU (with CPU parity), outputting both `ao.png` and world-space `bent_normal.png` (`withOcclusion` Joint-Bilateral-Upsamples lower-res AO into 4K/8K ORM maps without crease or gutter bleed). |
| Bake | `src/core/export.ts`, `src/core/ktx2.ts`, `src/core/zstd.ts` | The texture is the bake: gutters are padded, then exported as glTF 2.0 in standard `'png'` or UASTC + RFC 8878 Zstandard KTX2 (`format: 'ktx2'`, `KHR_texture_basisu` + `KHR_SUPERCOMPRESSION_ZSTD`, cutting GPU VRAM 4× and disk size >3×, streamed via `KTX2Loader`). |
| Walk | `src/core/walk.ts` | First-person walk through the level in the viewer. The body is a capsule that slides along walls (three-mesh-bvh); the feet follow the floor by a ray, so stairs and kerbs up to 0.55 m are climbed and anything higher blocks. It starts at the planned player spot nearest what the camera was looking at. |

`samples/loft.glb` (`samples/build_loft.py`, also Blender) is the Hall with more to it: walls with real window openings and steel frames, I-section girders and joists, a duct and a sprinkler pipe, stairs with treads and rails, a kitchen, furniture, and outside the windows the buildings across the street, two of them low enough to show a roof with a water tower. It names its 28 parts, so no vision model is needed. Its neighbours' roofs are floor a player cannot reach, so it is planned with `--area=-10,0,-5,10,6,5` (min x, y, z then max): camera spots are only placed with the eye inside that box. The Loft entry in the app's level menu sets it.

`samples/luxor.glb` (`samples/build_luxor.py`) is an Egyptian temple after Luxor Temple at about half its size: the end of the avenue of sphinxes, an obelisk and two seated colossi before the pylon, the pylon with its flagpole niches and gateway, a court with a portico of papyrus-bundle columns, an offering altar and standing kings, and the great colonnade of open papyrus columns under their architraves, roofless as it is today, with steps up to the sanctuary doorway. It names its 29 parts. It is the sample for a place with a look of its own: `node scripts/texture.mjs --look samples/luxor.look.json --id luxor --first h3 --fill h3 --views 64 --cleanup 8 --finish --layout near --pages 4 --atlas 4096` paints it from the photos in `references/luxor/` (credits in `references/luxor/CREDITS.md`). On two test views MiniMax H3 carved the walls and columns in legible relief and kept close to the photos' stone; FLUX 3 Klein, a quarter of the price, came out paler with flatter, vaguer carving, and ignored a change of colour in the wording that H3 followed.

`samples/hangar.glb` (`samples/build_hangar.py`) is the machine hangar of a police unit on a concrete platform in the sea, after the hangars of late-1980s mecha anime: a steel hall with trusses, a crane and a mezzanine office over a control corner; a white patrol robot in a maintenance gantry with hoses hanging to it, an orange construction robot and a transport truck; and outside the door an apron walled in by stepped concrete blocks 9 to 15 m high, with more platforms across the water. It names its 65 parts, each robot one part. It is the sample for a place that is painted and not photographed: `samples/hangar.look.json` sets `--wording cel`, which asks for a frame of a hand-drawn film (a gouache background, machines drawn as cels) and tells the model its reference pictures are frames of that same film to match in palette, line and design, where photos of a real place are only read for their surfaces. The look file expects six film frames under `references/hangar/`, which are not in the repository (they are not ours to share): bring your own, or drop `styleImages`. `styleMax` in a look file sends a view more references than its model's default of three or four. `spots` gives eye positions by hand: the planner joins standing spots by straight walks of a few metres, so a mezzanine or a gantry deck up a long flight of stairs gets no camera of its own (the Loft's mezzanine never had one), and the hangar names eight. On three test views FLUX 3 Klein came closer to the film than MiniMax H3 at a sixth of the price: soft gouache in muted blue-grey with thin lines, where H3 drew a graphic cartoon with heavy outlines; H3 kept the parts' named colours (a white robot, a green truck) and Klein painted the white robot grey.

The demo level (`samples/build_village.py`) names its parts through glTF materials ("house walls", "tiled roof", "stone stairs", "wooden barrels", ...), which is what the prompts read. It also unwraps by importance: surfaces players walk past get 62% of the texture, roofs 14% and outer walls 6%. Levels without part names still work: roofs are found by slope and height, and prompts go without a parts list.

The AI sky backdrop averages sky pixels only from views whose model painted the whole frame (Klein). Masked fills leave the clay sky as it was.

## The demo

The village in the video is run `village-07`: 128 views, $4.44 and 26 minutes on fal, painted one view at a time under
overcast light. 88 views come from where players stand, 20 from over the roofs, 11 from around the outside and 9 fill
holes. It's shown lit by a real sun, which swings round in the last shot.

`src/demo.ts` and `scripts/capture.mjs` replay a saved run wave by wave and render the frames straight off the WebGL
canvas. `video/compose.py` lays them out in Patch's video style (`video/lightsdown.py`): the clip in a plain frame with
the pink patch on its corner, one caption line under it, the label beside it. `video/audio.py` mixes the score and UI
sounds, and `video/encode.sh` muxes the result. `docs/readme/make_art.py` draws this README's header and footer.

The layout uses Patch's brand kit, which isn't in this repo: Patch Pixel is Patch's own typeface. Put the kit at
`./brand-kit` (or point `PATCH_BRAND_KIT` at it) to rebuild the video or the README art.

## Known limits (next up)

- **The ground.** Painted from eye height, most of it is seen at under 20° and comes out stretched (82% of the painted ground on the Courtyard). The floor pass (`--floors`) fixes the stretch but not the material: each floor view is its own painting, and across 16 of them the stones came out anywhere from 15 to 35 cm across and drifted from beige towards orange and blue-gray, whatever the prompt says about size. The ground pass (`--ground 3`) lays the ground from tiles instead, and on the Courtyard it replaced a patchwork of wedges of differing stones, a door smeared across the yard and a wedge of sky with one paving from wall to wall, for $0.04. Three things about it are not settled. The size of the stones is whatever the model drew, and the prompt's "about 3 metres across" does not fix it (the same words gave 17 stones across one tile and 40 across another): look at the result and lay it again with another `--span`, which is free. Tiles with a grain (rows of setts, boards) are laid without turning, and where patches meet their rows do not line up; square tiles and boards want a periodic layout this pass does not have. And it has been run on one level: not on an interior, and not with more than one ground material.
- **Interiors need more camera spots.** With spots every 4 m the Hall gets 8, and half of what was still unpainted after 44 views could not be seen from any of them; more views from the same spots only repainted what the blockout check had already rejected. Topping up with `--spacing 2 --look-at 2 --objective sharpness` (27 spots, cameras aimed at the gaps) closed 37% of the remaining gap in six views with little held back, taking the painted share of what players can see from 93% to 95%. The default spacing is still 4 m.
- **Part textures are softer than the views' paint, and only as good as their still.** The crates, replaced whole from a still, are coherent on every face but visibly less sharp than the planks the views painted. A still taken from the wrong place teaches the model the wrong thing: one aimed down at an unpainted crate top got back a blank texture, which is why stills are now only taken from the part's own floor and only when they show the part mostly painted.
- **Nothing yet keeps a part one material across views.** One Loft column came out pale steel in a view where the rest are black. Comparing each view's new paint with what the part already had, in view, does not separate that from lighting: on the Loft, painted with sun and shadow baked in, a part's new paint is legitimately anywhere from 0.3 to 3 times as bright as its old, so a tone test would reject good work. The part pass gives a part one material where it runs; the views do not.
- **Outdoors the system works without the floor pass.** On the Loft it leaves nothing bare and 95% of what players see painted by a view or a part texture. On the Courtyard, `--full` (22 views and three parts, $1.49) leaves nothing bare, 93% painted, and is sharper than the earlier run (50 against 41 px per metre at the median), with walls and the archway painted cleanly. The same run with the floor pass first (34 views, $1.65) came out worse: the ground as large square pavers where the look asks for cobbles, and a wall under the arch painted as an alley, since every later view started from that floor and continued it. Without the floor pass the ground is cobbles again but keeps the stretched bands of ground seen at a low angle, and the fountain came out plainer than in the earlier run. The ground pass was built for that (see The ground above).
- **MiniMax H3 Image (`--first h3 --fill h3`), tried on single Courtyard views, not on a run.** It takes no mask and no seed, so the same call twice gives two different paintings and every comparison here is one sample. What it does better than FLUX 3 Klein: it holds the blockout. On the same first view Klein put a tiled eave on a flat-topped wall and turned a block into a little tower; H3 kept the wall's flat top, the block and the raised panel (a door went exactly into it) in all thirteen first views painted with it. It is not free of inventions: in six of them it cut an open arch with sky behind it into a solid wall whose part is named "stone archway", and once it made the barrel a stone drum. Asked to fill a gap, it painted bare wall in crisp detail where Klein's was soft. What it costs: $0.034 a view at 2048 px (Klein $0.014) and 27 s; $0.082 and 45 to 65 s at 4096 px, where the detail is real (twice the fine detail of its own 2048 px view scaled up, by edge energy) and the pipeline ran with 4096 px views. Its paving came out as squared setts where the look asks for rounded cobbles, and it paints fewer windows. Wording matters less than expected for fidelity and more for finish: "a documentary photograph ... 24 mm lens at f/8" gave the most fine detail (28.7 on that measure, Klein 26.3), "next gen AAA game texture" the least (20.1), a cleaner, game-art look with a cast shadow nobody asked for; a one-line prompt lost the overcast light (sun, shadows, blue sky), since the model writes its own long prompt from whatever it is given. A diffuse pass can be asked for (`--diffuse`): described as the unlit base-colour view of a game engine with no shadows, no darkening in corners and no highlights, H3 painted flat colour, and the wall's brightness followed the render's light half as much (correlation 0.16 to 0.20 against 0.37), at the price of a plainer texture with larger stones. Removing the light from an already painted view as an edit did not work: the layout stayed stone for stone but wall, door and barrel all turned one salmon colour. `--diffuse` has only been tried on H3 first views.
- **H3 on whole runs, and what wording does to them (Loft, six runs of 22 views, $0.96 each, about 16 minutes).** Coverage does not depend on the wording: every run painted 90% of what players see and left 9.5% to the fill. The look does. Under the `indoor` blockout light, whose render has hard sun patches on the floor, the standard wording, "a documentary photograph" and "next gen AAA game texture" all bake those patches into the floor, and since each view paints its own, the floor comes out blotched; the AAA wording is the most contrasty and had the most held back for painting over the blockout (5.3% of a view on average, against 2.3% and 3.1%). The albedo wording (`--diffuse`) gives an even floor and a texture with less shading in it (surfaces in corners 25% darker than in the open, against 45%), but it is not usable for a run yet: after a clean first view, later views left furniture gray and painted stretches of brick wall white. Two things calm the picture. The blockout itself: `--lighting indoor-soft` puts the sun nearly overhead, so it lights what is outside the windows and the room has no sun patches for the models to copy. And the wording: of five calm ones tried on one view, "an unedited location-scouting photo, straight out of the camera ... neutral exposure, low contrast, muted natural colours, no colour grading" (`--wording scout`) was the most subdued (saturation 0.20 against 0.25 for the AAA wording, 2% of pixels blown out against 8%), and all five removed the sun patches even from the old blockout when told the patches are the blockout's own lighting.
- **Reference images with H3: one to three help, many pull the picture away.** H3 takes up to 16 images, about $0.008 each. For the ground tile, one photo of the painted ground brought the tile to the views' look (colour distance to their ground 4.7, against 13.8 with none: squared setts became the rounded cobbles the views had); three and six were no closer (6.8 and 9.6), because the views' own ground differs from view to view and the tile averages them. For filling holes, one to three earlier views of the same end of the room made a hole's content agree with them (a table's base came out as the wood of the table elsewhere, where without references it was white blocks). At 7 and at 15 references, one of the two views tried at each count stopped being an edit: the model composed a new picture of the room from another camera (what was already painted moved by 24 to 34 colour units, against 5 to 12 for the edits) and once dropped the table. So references are worth sending in ones and threes, nearest views first. This is not in the pipeline yet. The highspeed endpoint painted the same hole views in 19 to 20 s where the standard one takes 25 to 27, at twice the price, with no difference to the eye.
- **Notes on the blockout (`--notes`, H3 only).** H3 reads writing. A render marked up in red (an outline where the thing goes, a label with the words, an arrow) and a prompt that calls the marks an art director's instructions got a poster, a rug and a run of spiral duct painted where they were marked, at the size of the outline, with none of the red left; asked for in words alone the same three came out too, but the rug larger and further forward and the duct shorter. Notes are pinned to spots in the level (`src/core/notes.ts`), so each view that sees a spot is told the same thing until one has painted it. Flat things only: a duct painted on a wall is a picture of a duct.
- **H3 draws material maps; it does not measure them.** Asked for the normal, height, roughness and occlusion maps of a ground tile ($0.03 each), it returns images that look the part, with the stones redrawn: simpler outlines, moved a little. The edges of its height map agree with the tile's at 0.52 where PATINA's agree at 0.84. Its normal map is not a field of unit vectors (70% of pixels within a tenth of unit length, PATINA 97%) and tilts three times as hard (35° on average against 13°), with rainbow gradients across single stones. Its roughness is one arbitrary gray per stone (correlation with PATINA's: 0.00). Its height and occlusion are the usable two as pictures (stones light, joints dark, 0.81 with PATINA's height), but they do not sit on the texture's own stones, so laid over it they would shade the wrong places. PATINA stays the model for maps (`--pbr`); what H3 can add is a colour pass with less light baked in for PATINA to read (see `--diffuse`).
- **Things at the rim of a view, and windows from close up.** Traced on the Courtyard: a half window and a door 40 cm wide both came from the outermost 1.5% of one view, where the model had let a window and a door peek into the frame, and only that sliver reached the wall. `--frame-margin 0.04` leaves the outer 4% of every image unpainted; replaying the run with it, both are gone. It is not the default yet: no full run has been painted with it, and it costs coverage the later passes must make up (in the replay a balcony painted only at a rim went back to the fill). The other fault was a row of doll-sized windows: a clean-up view standing 3 m from a wall, asked to fill a gap, painted a facade at its own scale. Telling it "no new windows or doors" made it paint two doors and a shutter (what a prompt names, the model paints), and a prompt with no look at all left the wall gray. What worked, on that one view: the look with its clauses about doors, shutters and windows taken out, and the gap described as more of the bare wall beside it. Hole and clean-up views are now prompted that way (`plainFills`); views of whole walls still place the windows.
- **Filled is not painted.** The finishing fill leaves no clay, but what it colours has no detail of its own: a part nothing painted comes out one flat colour (the Loft's mezzanine floor, where the planner puts no camera). On the Loft that is 9% of what players see, spread over beams, window frames, joists and the buildings outside. The clean-up pass gives up on those when the blockout check rejects two views in a row.
- **Conditioned inpainting was tried and is not used.** On four Loft views, FLUX.1 dev inpainting with a depth ControlNet (fal's `flux-general/inpainting`) kept the blockout best of all (under 2% painted over), but its brick and floor did not match what was already painted, it took 14 to 118 s a view and costs $0.075 a megapixel. SDXL ControlNet Union inpainting with depth and normal maps invented structure as often as Fibo. Klein, with no control image at all, was within a few points of the depth-conditioned model and matches the existing paint.
- **What gets projected.** Two rules can now be set per run and are recorded with it. `--min-cos 0.2` stops a view painting any surface it sees at under about 12°: replaying the Courtyard run with it removes every stretched band of ground, and leaves that ground unpainted instead (89% of what players see painted becomes 78%), for the floor pass, a later view or a top-up to fill. It is off by default until a whole run has been painted with it. `--edge-guard 6` leaves a farther surface unpainted right beside a nearer one's outline; on replays it cost 1 to 12 points of coverage and did not remove the ghosts it was meant for, so it stays off. Those ghosts (glazing bars across the buildings outside the Loft's windows) are the model painting its own bars, differently spaced, over the view: nothing near a real outline. `--check-cells` has the plane test also hold back, cell by cell, patches of a flat face that the painting shows as another surface; it runs (3 to 16% more of each view held back on an 8-view replay) but what it holds back has not been looked at, so it is off too.
- **Resolution.** Views are 2048 px by default (`--view-size 1024`, or the view size menu, for quicker and slightly cheaper runs with about half the detail). A saved run is replayed at the size it was painted at. FLUX 3 Klein really paints 2048 px, for $0.014 a view instead of $0.009; Fibo 2 paints about a megapixel whatever it is sent and scales it up, so its fills are recorded as half as detailed and a sharper view may paint over them. On the Courtyard (12 views, 4 hole views, 4096 px texture) 2048 px views instead of 1024 px ones raised the detail on the painted surface from 24 to 41 px per metre at the median and the share of the texture with a view pixel or more per texel from 7.9% to 15.9%, for $0.85 instead of $0.71 and 9.6 minutes instead of 5.7, one run each. With views that sharp the texture becomes the limit on the nearest surfaces, which is where `--layout seen` adds to it (mean 31 to 38 px per metre on the same run). The plane check is sent a megapixel at most, so it costs the same at either size. A run's folder is about 2.5 times larger at 2048 px, and each view keeps its composite in memory for the run record, about 2 GB over a full Village run.
- **Some outer walls stay gray.** Walls facing narrow gaps between buildings aren't seen well by any camera yet.
- **Misprojections.** Overhangs (like the arcade ceiling) can catch misprojected fragments. The blockout check keeps repainted scenes and sky patches off the level, but only on faces over 0.4% of the frame, and one threshold decides: a face painted in two clearly different materials counts as replaced and stays unpainted until a hole view does better. A prop the models keep merging into the wall or the ground behind it ends up with that texture after its second go. Some cameras can't be painted faithfully at all: a hole view looking steeply down a blank wall comes back as a street or a house front every time, so that wall stays unpainted until another camera sees it. The plane test only looks at flat faces over 10% of the frame. Next is an automatic retouch pass for seams and odd patches.
- **Views painted from bare clay drift in style.** Each invents its own paving and plaster until it overlaps something painted. `--style-reference` (off by default) shows such views a sheet of material samples cut from the texture so far. Handing the model a neighbouring view's photo instead, as WorldMesh does, made it return that photo for three of five test cameras; the sample sheet did that for one, and brought paving colours only about 17% closer. Views with too little in them get no sheet.
- **Sharpness is limited by the texture's layout and the view budget, not by which cameras are picked.** On the Courtyard, cameras at player height can see 30% of the texture at all (64% on the Village): the level's UVs give undersides and hidden faces the same resolution as the walls players look at. Twelve 1024 px views then leave half the painted texture at under 0.5 view pixels per texel on a 4096 px texture. Picking cameras for sharpness instead of coverage (`--objective sharpness --look-at 2`) was tried and measured: 43% of the texture painted instead of 35% and 16% context instead of 10%, but the same detail over the texture (19.2% against 18.8% of what its resolution could hold), fewer cells at full detail (5.9% against 7.9%) and $0.78 instead of $0.71, one run each. So it is off by default. A texture layout weighted by what players can see (`--layout seen`) helps where the texture, not the views, is the limit: replaying the same 21 Courtyard views into both layouts, the mean detail on the painted surface goes from 10 to 12 px per metre on a 1024 px texture (median 12 to 18), from 17 to 21 on a 2048 px one (median unchanged at 24) and from 26 to 29 at 4096 px. So a 2048 px texture on that layout sits about halfway to a 4096 px one on the file's UVs, and at 4096 px with this few views it changes little. More or larger views are what raise the ceiling (see Resolution above). `scripts/measure.mjs` reports these numbers for any saved run.
- **Part names are guesses.** A vision model names each shape from one picture. A level welded into a single shape gets one name for everything, and a wrong name misleads the painter the way a right one guides it, so look over the Parts list. Naming parts in the file is still better.
- **Floor clutter from down-looking views.** Floor views make the models paint crates and debris onto the ground, so they're off (`downYaws: 0`). Floor views need their own prompt, or the normals check from the spike.
- **No local models yet.** *(Updated: `src/providers/local.ts` and `src/providers/router.ts` now route `--provider local|auto` to loopback ComfyUI `:8188`, diffusers `:8000`, and Hunyuan3D-Paint `:8081` at $0 without `FAL_KEY`.)*
- **Albedo is approximate.** Overcast painting removes cast shadows, but the models still paint some soft shading and contact darkening. *(Updated: `src/core/uv-refine.ts` (`--uv-refine`) regresses per-part low-frequency log-luminance against the 3D normal/position sun + sky irradiance basis, cutting residual directional shading correlation by >90%.)*
- **The maps are detail only.** The normal map holds relief up to about 1% of the texture's width (stones, frames, slats); anything broader is removed with the lean the model adds. *(Updated: `src/core/pbr.ts` and `src/core/aligned-maps.ts` now add metallic, refined micro-normals and convex-edge wear alongside POM height and roughness, plus `metal` / `hard-surface` / `fabric` / `organic` presets and separate linear PNG exports.)*
- **No UV unwrapping.** *(Updated: `src/core/unwrap.ts` runs `xatlas` automatically when UVs are missing, overlapping or degenerate, and `--weights` / `--paths` weight UV layout density on any mesh.)*
